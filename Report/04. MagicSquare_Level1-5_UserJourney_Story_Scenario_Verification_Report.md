# Magic Square 4x4 TDD Practice Report (Level 1-5)

## 1) Document Purpose
This report consolidates the planning and verification outputs produced for the Magic Square project across:
- Level 1: Epic
- Level 2: User Journey
- Level 3: User Stories
- Level 4: Technical Scenarios
- Level 5: Scenario Verification and Summary

The focus is on invariant-driven design, contract clarity, dual-track TDD readiness, and traceability.

## 2) Project Context
- Project: Magic Square 4x4 TDD Practice
- Top Epic: "불변식 기반 사고 훈련 시스템 구축"
- Goal: Train design quality through Concept -> Invariant -> Contract -> Test traceability rather than answer-hardcoding.

Core rules:
- Input is a 4x4 int matrix.
- `0` means blank.
- Exactly two blanks are required.
- Values must be `0` or `1..16`.
- Non-zero duplicates are not allowed.
- Magic constant is `34`.
- Output is `int[6]`.
- Coordinates are 1-indexed.
- Output format is `[r1, c1, n1, r2, c2, n2]`.

## 3) Level 1 Epic Summary
Epic title:
- 불변식 기반 사고 훈련 시스템 구축

Business and learning direction:
- Shift from answer-first coding to invariant-first design.
- Apply dual-track UI/Boundary and Logic/Domain TDD.
- Preserve external contracts through refactoring.

Success criteria baseline:
- High domain logic coverage target.
- Full boundary input validation contract pass target.
- No unexplained magic numbers.
- Use named constants (e.g., `GRID_SIZE`, `MAX_VALUE`, `MAGIC_CONSTANT`).
- No hardcoded final answers.

## 4) Level 2 User Journey Summary
Journey stages:
1. Problem Recognition
2. Contract Definition
3. Domain Separation
4. Dual-Track TDD Progress
5. Regression Protection

Journey intent:
- Reframe the problem as invariant training.
- Define contracts before implementation.
- Separate domain responsibilities (`BlankFinder`, `MissingNumberFinder`, `MagicSquareValidator`, `Solver`).
- Execute RED/GREEN/REFACTOR in dual-track style.
- Protect contracts and invariants through regression-oriented scenarios.

## 5) Level 3 User Story Summary
Story set:
- Story 1 (Boundary): Input validation before domain call
- Story 2 (Domain): Blank coordinate discovery
- Story 3 (Domain): Missing number discovery
- Story 4 (Domain): Magic square validation
- Story 5 (Domain/Control + Boundary output): Two-combination solving and output contract

Quality points:
- Boundary and Domain stories are separated.
- Each story carries protected contract/invariant statements.
- Acceptance criteria are written in testable and measurable form.
